# 模拟面试记录 — Mini Claude Code 项目

**岗位**: AI 应用开发工程师
**项目**: Mini Claude Code — 轻量级本地 Coding Agent

# 简历上的项目描述
MiniClaudeCode：基于Harness Engineering的Coding Agent CLI
技术栈：Python、Anthropic/OpenAI API、 AsynclO、 CLI (Rich) 
项目概述：面向编码场景，聚焦长程任务稳定执行的轻量级本地 Agent，围绕工具调用、上下文管理、任务恢复、结构化记忆、运行审计和评测闭环做系统化设计。重点解决工具可控调用、上下文可持续、权限安全可预期的问题。
1.	Agent 循环与工具系统：统一接入 Anthropic/OpenAI兼容后端，构建ReAct核心循环，实现流式输出与指数退避+抖动重试机制，利用 Anthropic 后端机制实现流式工具执行与工具并发回退，多工具执行时间相比完整接收API返回后统一进行工具调用平均降低15%；实现13个核心工具，通过部分工具的延迟激活，降低上下文开销，前5轮对话中平均节省7k+ Tokens。
2.	上下文压缩与记忆：实现4层压缩流水线，达到从工具结果轻量级截断到全量摘要逐级递进的渐进式压缩；结合语义召回、异步预取和新鲜度提醒，维持长会话上下文密度并避免过期信息误导，实现跨会话记忆，让Agent在多次对话间保持对用户和项目的认知，不依赖对话历史。
3.	权限与安全：设计5种权限模式，叠加”模式控制+声明式 allow/deny 规则+危险命令正则检测+用户确认”四层权限体系，平衡自动化效率与高风险操作可控性；对编辑文件操作启用 read-before-edit 与编辑时间校验双重保障，降低文件误改风险。
4.	可观测性与运行追踪：设计事件驱动的观测体系，基于 Observer 模式在 Agent 双后端循环中全链路埋点（turn_start / first_token / turn_end / tool / compaction），每次对话自动生成结构化 JSONL trace 文件。按 ask 聚合、单轮粒度记录首Token延迟、Token消耗、缓存命中率、工具调用耗时、压缩触发等指标，为性能分析与问题定位提供数据基础。
5.	自动化回归评测：构建 benchmark 评测框架，定义 12 个标准化回归任务覆盖文档编辑、文本修改、工具边界恢复、编程实现 4 个场景类别。Runner 通过 --yolo 模式自动化执行（隔离工作区 + verifier 驱动通过判定），结合 trace 模块自动提取性能指标。支持多次运行取均值与标准差，输出聚合报告，形成”功能正确性 + 性能稳定性”双维度评测闭环。

## Q1: 流式工具执行的原理和 15% 的性能提升

**项目描述**: 利用 Anthropic 后端 Message Block 机制实现流式工具执行，多工具执行时间平均降低 15%。

**你的回答**:
> 实现原理是 Anthropic 返回格式是 Message Block，每个 Block 有明确的类型和终止标识（content_block_stop）。通过捕获 tool_use 类型的 Block 并监控终止标识，在 tool_use Block 结束后立即传入工具调用分发器执行，实现工具的流式调用。Baseline 是完整接收所有信息流后才开始执行工具调用。
>
> 15% 这个数据通过自定义的 5 个场景（前端代码构建、Bug 修复、小游戏实现等），控制相同环境和 prompt，分别多次实验后取平均值得到。

**补充建议**:
> - 可以考虑把 "15%" 改为"场景实测中观察到约 15% 的性能提升"，避免面试官追问统计细节（置信区间、方差等）
> - 可以补充说明并发安全的工具（只读类）才提前执行，写操作工具仍需等待权限确认后再执行，避免误改风险

## Q2: 4 层上下文压缩流水线

**项目描述**: 从工具结果轻量截断到全量摘要递进，维持长会话上下文密度。

**你的回答**:
> **第 1 层 — 工具结果轻量截断**: 工具结果过长时，只保留头部和尾部，中间用标识符代替；超过 30KB 的工具结果自动写入本地磁盘，供模型按需检索。
>
> **第 2 层 — 过期结果清理**: 对同一文件的重复读取，只保留最新的读取结果，历史读取结果用占位符代替（`[Old result cleared]`），告诉模型曾经读过但内容已清理。
>
> **第 3 层 — 闲置时间激进清理**: 用户长时间未发送消息时，服务端 kv-cache 已经被清理，此时会做更激进的清理，只保留最新的 3 个工具结果。
>
> **第 4 层 — 全量压缩**: 上下文超过 70% 占用阈值时，启用另一个模型对历史消息进行摘要替换。压缩时排除系统提示词和用户最新一轮消息，通过 prompt 要求模型保留任务决策、文件路径、任务进度等关键信息。

**补充建议**:
> - 可以补充各层的触发条件: 第 1 层在每轮 API 调用前执行；第 2 层在上下文利用率 > 60% 时触发（`SNIP_THRESHOLD`）；第 3 层在空闲 > 5 分钟时触发；第 4 层在利用率 > 85% 时自动触发
> - 这是一个"渐进式"设计的典型案例——轻量操作在前，重操作在后，能省则省

## Q3: 语义召回与异步预取

**项目描述**: 结合语义召回、异步预取和新鲜度提醒，实现跨会话记忆。

**你的回答**:
> 语义召回是用户每次发送新消息时静默启动一个 sideQuery，使用 LLM 对记忆索引（MEMORY.md）进行检索，返回相关记忆。索引只包含记忆的名称和摘要，每条不到 20 tokens。异步预取在用户发送新消息时与第一次 API 调用并行执行，在后续每轮循环中检查预取是否完成，完成后注入上下文并标记为已消费。
> 读取索引时只读前 200 行、超过 25KB 的索引会被截断，防止异常情况
> 如果用户消息过短且无空格（如单独的 "yes"、"no"），则认为没有检索必要，跳过。记忆的召回由大模型决定。

**追问 — SideQuery 不是 embedding + 向量检索？**
> 第一，每条记忆长度要么太短要么可能太长，RAG 的切片模式不适合对记忆做处理。第二，便于维护——RAG 需要维护向量数据库，每次记忆改动要增量更新、删除旧索引甚至重建索引，对本地 Agent 来说太"重"了。并且，记忆选择是**语义推理**任务而非**语义匹配**任务。RAG 做的是"这段记忆和 query 像不像"，而你需要的是"这段记忆对当前任务有没有用"——这是推理问题，LLM 来做更合适。关于单轮对话预取来不及完成的情况——这是刻意的设计权衡，优先保证首字延迟体验。真正需要记忆的场景往往是多轮工具调用，那时预取早已完成

## Q4: 权限与安全体系

**项目描述**: 5 种权限模式 + 4 层权限体系，叠加模式控制、声明式规则、危险命令检测、用户确认。

**你的回答**:
> 权限判断按优先级：运行模式（最高优先级）→ 权限规则（deny 优先）→ 人工确认。对于 shell 命令还有额外的关键词匹配，检测危险模式。对编辑文件有 read-before-edit + mtime 校验的双重保障。五种权限模式分别是：`default`（需确认危险操作）、`bypassPermissions`（--yolo，全放行）、`plan`（只读）、`acceptEdits`（自动批准编辑，shell 仍需确认）、`dontAsk`（CI 用，全部自动拒绝）。

**追问 — 修改系统配置文件时，4 层体系如何工作？**
> 会话开始前加载预定义权限规则。如果处于 bypassPermissions 模式直接放行；如果是 plan 模式直接拒绝。不在以上模式时，先看权限规则中有无该路径的定义，有冲突时 deny 优先。规则没有定义则交给人工确认弹窗。Shell 命令会额外做危险关键词正则匹配。

## Q5: Read-before-edit 与编辑时间校验

**项目描述**: 双重保障降低文件误改风险。

**你的回答**:
> Agent 修改文件前必须先读取。修改时会检查文件的 mtime，如果与读取时不一致，说明用户在这期间手动修改了文件，Agent 会重新读取、基于最新内容再修改，避免覆盖用户的改动。

**追问 — 用户和 Agent 同时编辑不同行怎么办？**
> 确实会覆盖或丢失一方的修改。但实际场景中用户和 Agent 同时改同一个文件概率极低，这是一个工程上的可接受风险，不值得为此做行级合并的复杂度。

## Q6: 可观测性追踪（Tracing）的设计

**项目描述**: 基于 Observer 模式的事件驱动观测体系，全链路埋点记录 Agent 运行指标。

**你的回答**:
> Agent 的两个后端（Anthropic / OpenAI）在核心循环的关键节点向 Canonical RuntimeEvent ledger 发射事件：turn_start、first_token、turn_end、tool_start、tool_outcome、compaction、permission。Metrics Projection 从 Canonical Events 重建首 token 延迟、Token 用量、工具调用耗时、重试和终态等指标，并与 Session/Model Replay/Recovery 共享同一事实源。
>
> 这些指标不再依赖独立 trace 文件；Session、Metrics 和 Trace 都是可删除、可重建的 projection，Canonical SQLite ledger 记录事件顺序、工具 durable boundary 和 terminal seal。

**追问 — 为什么不直接用 logging？**
> 文本日志无法同时承担不可变事实、事件关联和恢复边界。Canonical 事件使用严格 envelope、session/turn/run/invocation identity、store-assigned ordinal 和 digest；Metrics 等消费者再按需投影为可计算视图。

**追问 — 事件发射会影响 Agent 性能吗？**
> 事件提交是同步 durable boundary，确保工具副作用前的 dispatch 已落盘；Provider request 数组只是从 Canonical Replay 物化的临时上下文。代价是必要的 SQLite 写入，但避免了事实丢失、双写不一致和恢复时的隐式重放。

## Q7: Benchmark 评测框架

**项目描述**: 12 个标准化回归任务 + 自动化 runner + 多轮聚合报告。

**你的回答**:
> 评测框架分三层：task 定义层（JSON，含 prompt、fixture、verifier、category）、runner 执行层（subprocess 调用 `--yolo` 模式，隔离工作区，串行执行）、reporter 聚合层（从 trace 提取指标，支持多轮均值/stddev）。
>
> 12 个任务覆盖 4 个类别：documentation（文档修改）、text-edit（精确文本替换）、tool-boundary（异常恢复，如无效 patch、路径逃逸、重复读取）、coding（创建模块、修复语法、写测试、重构、跨文件搜索替换）。每个任务有独立的 verifier 脚本，退出码 0 表示通过。
>
> 支持 `--runs N` 多次运行，reporter 按任务聚合各轮指标计算 mean ± stddev。例如 `add_unit_test` 耗时 10792±509ms，`create_python_module` 耗时 2750±28ms，可以直观对比不同任务类型的耗时和稳定性差异。

**追问 — 为什么用 subprocess 而不是直接 import Agent？**
> 进程隔离。subprocess 调用的是用户实际使用的 CLI 路径（`python -m mini_claude --yolo`），测试的是真实运行环境。直接 import Agent 会共享内存状态，残留的 session、memory、MCP 连接会影响后续任务，破坏独立性。

**追问 — 评测中发现的典型问题？**
> 2 个 verifier 本身有语法错误——inline `python -c` 中不能使用 `try/except` 和多行 `for` 循环。这说明评测框架本身也需要被验证。另外 `cache_hit_rate` 初始实现用累加值除以总输入，多轮对话中 cache_read 远大于单轮 input，导致比率 > 1。修复为每轮分别计算后取平均，得到有意义的 0-1 指标。
